🛡️ Core Safety Architecture (Deterministic Policy Engine)

The policy_engine.py module is the immutable mathematical firewall between conversational AI proposals and Razorpay order execution:

python (backend/services/policy_engine.py) 
def validate_offer(original_price: float, proposed_price: float, policy_rules: dict) -> dict:
    # Pure Python — Zero LLM involvement
    max_discount = policy_rules.get("max_discount", 10)
    min_price = policy_rules.get("min_price", 100)
    max_auto_order = policy_rules.get("max_auto_order", 50000)

    # 1. Direct list-price purchase check (0% discount)
    if proposed_price >= original_price:
        return {"approved": True, "reason": f"Direct purchase approved at list price ₹{proposed_price:.2f}"}

    # 2. Max discount limit validation
    discount_pct = ((original_price - proposed_price) / original_price) * 100
    if discount_pct > max_discount:
        return {"approved": False, "reason": f"Discount of {discount_pct:.1f}% exceeds max {max_discount}%"}

    # 3. Dynamic price floor (capped by product list price)
    effective_min = min(min_price, original_price)
    if proposed_price < effective_min:
        return {"approved": False, "reason": f"Price ₹{proposed_price:.2f} is below minimum ₹{effective_min:.2f}"}

    return {"approved": True, "reason": "Offer approved within merchant policy limits"}
💡
Dynamic Price Floor Invariant: If a catalog item is listed under ₹500 (e.g. movie ticket at ₹420), the effective floor is dynamically calculated as min(policy_min_price, catalog_price) so valid purchases are never blocked.

🔄 The Safety Pipeline (Step-by-Step Flow)

Every transaction passes through a 6-stage deterministic security pipeline before funds are settled:

1
Rate Limiter

Enforces maximum 5 negotiation attempts per product in a 10-minute rolling window.

2
Anomaly Detector

Automatically flags and blocks any offer demanding >50% discount as automated abuse.

3
LLM Proposal Generator

Ollama (llama3.2) drafts conversational counter-offer text. Has zero execution privileges.

4
Deterministic Policy Engine

Mathematically verifies price, discount %, price floor, and auto-order threshold ($2,50,000).

5
Pre-Response Audit Ledger

Writes decision, actor attribution (UID/Role), and local IST timestamp to SQLite & Firebase RTDB.

6
Razorpay Order Issuance or Red Card

Approved offers create a Razorpay test order; blocked offers return a zero-payment red card.

📊 4-Factor Trust Scoring Algorithm

Merchants receive a composite 0–100 trust score computed by trust_scorer.py.

Formula Breakdown

Score = (Completeness × 0.35) + (Settlement × 0.30) + (DisputeRate × 0.20) + (Freshness × 0.15)

  • Catalog Completeness (35%): Coverage of price, stock, category, delivery days, returns.
  • Settlement Consistency (30%): Ratio of paid vs. created orders.
  • Dispute Inverse Rate (20%): Lower dispute frequency yields higher score.
  • Catalog Freshness (15%): Time since last manifest update.
Public Cryptographic Certificate

Merchants with trust scores > 80 earn a public badge (/merchant/:id/certificate) with an animated SVG trust ring and a deterministic SHA-256 verification hash:

🛠️ Failure Retrospective & Technical Learnings

In accordance with "Show one failure handled gracefully", here is the real-world retrospective on actual failures encountered and solved during the build:

Failure Incident Root Cause Engineering Solution Implemented Residual Risk
1. Scraper Blocking Amazon/Flipkart return HTTP 503/CAPTCHA on direct scrapers. Tiered architecture: Live fetcher → 15-min TTL cache → Curated seed fallback (marketplace_service.py). Seed data requires periodic refresh.
2. LLM Price Hallucination Ollama's llama3.2 proposed ₹50 for a ₹750 ticket (93% discount). Separated text from money. validate_offer() caught and rejected the proposal; logged in audit ledger. LLM can still generate optimistic text messages.
3. Cross-Category Search Noise Searching "spiderman" returned shoes & sarees alongside movies. Domain-specific mismatch guards in match.py zero-score cross-category contaminations. Products spanning categories require tags.
4. Payment Race Condition Frontend navigated to Orders before settlement API completed. Chained createOrder → completeTestPayment atomically in NegotiationCheckout.tsx. Network latency (>5s) shows brief spinner.
5. Token Normalization "spider man" returned 0 matches for "Spider-Man". Added alphanumeric token normalization (re.sub(r'[^a-z0-9]', '', kw)) in match.py. Short terms (≤3 chars) guarded with regex.
